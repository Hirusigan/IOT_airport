# Devtools and Docker deployment

The existing frontend-facing simulation control remains on the backend: `POST /api/devtools/simulation`, `POST /api/devtools/simulation/stop`, and `GET /api/devtools/simulation`. The backend's `SimulationRunner` fetches the scenario catalog from Airport Simulation, forwards start and stop requests, and polls its status. Airport Simulation controls scenario timing and event order, registers schedules, and records departures over HTTP. It sends device-action commands to IoT Device Simulator. IoT Device Simulator builds the event envelope and topic, then publishes the event to the named airport broker using anonymous MQTT.

Airport Simulation registers flights and devices, including scheduled arrival times when present, with `POST /api/airports/schedule` before its event clock starts. It does not submit a run manifest. At departure and arrival it sends actual flight times directly to the backend over HTTP; the gate departure and luggage scanner events also travel through MQTT. A first luggage check-in carries a planned flight ID, journey ID, trip ID, and leg order. Backend event processing creates the trip, journey, and assignment in the same transaction as that observation. This lets the existing luggage-state and alert rules process the first check-in without preloading assignments.

`compose.yaml` is the server runtime stack. It contains the default `regional`, `aar`, and `cph` Mosquitto services, PostgreSQL, backend, frontend, Airport Simulation, and IoT Device Simulator. Mosquitto ports stay on the private `airport-brokers` Docker network. Default broker configurations and ACLs are static files under `docker/mosquitto`; no bootstrap container or broker passwords are used. The backend and dynamic airport brokers share the named `airport-broker-config` volume.

Airport registration writes metadata to PostgreSQL, writes a code-scoped Mosquitto config and ACL into that shared volume, and starts a fixed `eclipse-mosquitto:2.0.22` container through Docker.DotNet. New brokers join `airport-brokers` and initiate an outbound bridge to `regional`. ACLs limit local airport topics and the regional broker permits `airport/#`. Anonymous ACLs cannot prove a broker's claimed client ID. The backend requires access to `/var/run/docker.sock` for provisioning.

PostgreSQL's password is set as `POSTGRES_PASSWORD` in `.env` (see `.env.example`). Keep `.env` and the database volume together. The backend and brokers have no published host ports. The frontend joins the existing external `ingress` network for the existing Cloudflare tunnel. Cloudflare Access configuration remains outside this repository.

The GitHub Actions workflow validates image builds on pushes to `main`. A manual dispatch on `main` with publishing enabled builds/pushes backend, frontend, Airport Simulation, and IoT Device Simulator images as `latest` and commit SHA tags, then requests a Watchtower update for each application container. Watchtower remains in its separate Compose file. Only these four applications have its enable label.

Adding scheduled and actual flight arrival fields requires the `AddFlightArrivalTimes` EF migration. No build, migration, or test command was run during this implementation.
