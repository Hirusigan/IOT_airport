# Simulation and MQTT contract

Airport Simulation controls a run and sends its flight schedule and source devices to `POST /api/airports/schedule` before publishing starts. The schedule includes a fresh UUID `simulationRunId`, flights with run-scoped IDs, UTC `scheduledDeparture`, optional UTC `scheduledArrival`, and the devices used by the scenario. Airport records are registered separately through `POST /api/airports` or supplied by the default AAR/CPH seeder. At departure and arrival times Airport Simulation records actual times directly through `POST /api/airports/flights/{flightId}/departure` and `/arrival`; gate and luggage scanner events are also retained in the MQTT event history. There is no run manifest or run-registration request.

Airport Simulation calls `POST /devices/actions` on IoT Device Simulator for each timed device action. IoT Device Simulator creates the event ID, envelope, and topic, then publishes to the action's airport broker. Each airport broker bridges only `airport/{airportId}/#` outward to `regional`; the backend subscribes to `airport/#` on the regional broker.

Topics use `airport/{airportId}/{deviceType}/{deviceId}/{eventType}`. Messages use QoS 1, retain false, and schemaVersion 1. Envelopes contain eventId (UUID), simulationRunId, occurredAt (UTC), airportId, deviceId, eventType, and data.

Luggage data contains luggageId, journeyId, sequence (positive per journey), stage (`checkin`, `security`, `sorted`, `loaded`, or `arrived`), optional flightId, optional tripId, and legOrder. A first `checkin` must contain the planned flightId. The backend validates the flight/run and creates its trip, journey, and assignment with the accepted observation. Later luggage events use that assignment; `loaded` events identify the observed flight. For later trip legs, the first check-in is accepted only after the preceding leg has confirmed arrival and departure/loading evidence.

Departure data contains flightId and departedAt (UTC); the backend records actual departure on the scheduled flight. Actual flight arrival is sent directly over HTTP and requires a recorded departure. A luggage `arrived` scanner event remains a separate bag-handling observation. Flight and device identities must exist before their events. Unknown identities and invalid topic/payload combinations are rejected and recorded as diagnostics.

The backend stores registered airports/devices, run-scoped flights, trips, journeys, assignments, raw accepted events, current luggage state, and alerts. Event IDs and alert keys are unique. Older sequences remain in history without replacing current state. Notifications follow transaction commit and prompt clients to refetch authoritative snapshots.

Mosquitto access is anonymous with ACL topic rules. Airport ACLs allow their own `airport/{CODE}/#` namespace and regional ACLs cover `airport/#`. These rules limit topics but do not authenticate a broker's claimed client ID. Brokers remain on the private Docker network without host-published ports.
